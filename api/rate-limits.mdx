The Google API enforces rate limits to ensure fair usage and consistent performance for every team on the platform. Limits are applied per API key on a rolling 60-second window. If your integration sends requests faster than your plan allows, the API returns a `429 Too Many Requests` response until the window resets. Understanding these limits — and building your code to handle them gracefully — keeps your integration reliable under all traffic conditions.

## Rate Limits by Plan

Your workspace's limit tier is determined by your current subscription plan. Limits apply **per API key per minute**.

| Plan | Requests per minute | Burst allowance |
|---|---|---|
| Free | 60 req / min | Up to 10 concurrent |
| Pro | 600 req / min | Up to 50 concurrent |
| Enterprise | Custom | Custom |

<Note>
  If your team needs limits beyond the Pro tier, [contact the Google sales team](mailto:sales@google.com) to discuss an Enterprise plan with custom rate limits tailored to your workload.
</Note>

## Rate Limit Response Headers

Every API response includes three headers that tell you exactly where you stand in the current rate-limit window. Read these headers proactively — don't wait for a `429` to start managing your request pace.

| Header | Type | Description |
|---|---|---|
| `X-RateLimit-Limit` | integer | Maximum requests allowed in the current 60-second window for your plan |
| `X-RateLimit-Remaining` | integer | Requests remaining in the current window |
| `X-RateLimit-Reset` | Unix timestamp | UTC epoch second when the current window resets and `X-RateLimit-Remaining` returns to the full limit |

### Example response headers

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 543
X-RateLimit-Reset: 1718099460
```

Calculate how long to wait before the window resets:

```javascript
const resetAt = parseInt(response.headers.get("X-RateLimit-Reset"), 10);
const secondsUntilReset = resetAt - Math.floor(Date.now() / 1000);
console.log(`Rate limit resets in ${secondsUntilReset}s`);
```

## The 429 Too Many Requests Response

When you exceed your rate limit, the API returns an HTTP `429` status. The response includes a `Retry-After` header (in seconds) and a JSON error body.

### Response headers on a 429

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1718099520
Retry-After: 38
```

### Response body

```json
{
  "data": null,
  "meta": null,
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "You have exceeded the rate limit of 60 requests per minute for the Free plan. Retry after 38 seconds.",
    "status": 429,
    "retry_after": 38
  }
}
```

Always check the `Retry-After` value (also available in `error.retry_after`) before re-attempting the request — retrying immediately will only produce another `429` and waste your quota once the window resets.

## Handling 429 Errors: Best Practices

### 1. Use exponential backoff with jitter

Retrying with a fixed delay can cause a **thundering herd** problem when multiple clients hit the limit simultaneously. Exponential backoff spreads retries over time, and adding random jitter prevents synchronized retry storms.

The following JavaScript utility implements truncated exponential backoff with full jitter. It respects the `Retry-After` header when present and falls back to calculated delays when it is not.

```javascript
async function fetchWithBackoff(url, options = {}, maxRetries = 5) {
  const BASE_DELAY_MS = 500;
  const MAX_DELAY_MS = 30_000;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      // Success or a non-retryable error — return immediately
      return response;
    }

    if (attempt === maxRetries) {
      throw new Error(`Rate limit still exceeded after ${maxRetries} retries.`);
    }

    // Prefer the server-supplied Retry-After value
    const retryAfterHeader = response.headers.get("Retry-After");
    const serverDelay = retryAfterHeader
      ? parseInt(retryAfterHeader, 10) * 1000
      : null;

    // Exponential backoff: 500ms, 1s, 2s, 4s, 8s … capped at 30s
    const exponentialDelay = Math.min(
      BASE_DELAY_MS * 2 ** attempt,
      MAX_DELAY_MS
    );

    // Full jitter: random value between 0 and the calculated delay
    const jitter = Math.random() * exponentialDelay;

    const delay = serverDelay ?? jitter;

    console.warn(
      `Rate limited (attempt ${attempt + 1}/${maxRetries}). ` +
      `Retrying in ${Math.round(delay)}ms…`
    );

    await new Promise((resolve) => setTimeout(resolve, delay));
  }
}

// Usage
const response = await fetchWithBackoff(
  "https://api.google.com/v1/projects",
  {
    headers: {
      Authorization: `Bearer ${process.env.GOOGLE_API_KEY}`,
      Accept: "application/json",
    },
  }
);

const payload = await response.json();
```

### 2. Cache responses where possible

Many read operations — fetching workspace configuration, user lists, or static project metadata — don't require a fresh API call on every action. Cache responses locally and only re-fetch when the data is likely to have changed or after a reasonable TTL (e.g., 60 seconds for lists, 5 minutes for configuration).

<Tip>
  Store the `updated_at` timestamp from list responses. Before re-fetching a resource, compare its cached `updated_at` against a lightweight `HEAD` or conditional `GET` request to skip the full fetch when nothing has changed.
</Tip>

### 3. Batch requests instead of looping

If you need to operate on many resources, avoid issuing one request per item in a tight loop. Use bulk endpoints where available (e.g., `POST /v1/tasks/batch`) and fetch pages at the maximum `per_page=100` to minimize total request count.

```bash
# Inefficient — one request per task ID
for id in task_001 task_002 task_003; do
  curl "https://api.google.com/v1/tasks/$id" \
    -H "Authorization: Bearer $GOOGLE_API_KEY"
done

# Efficient — fetch up to 100 tasks in a single request
curl "https://api.google.com/v1/tasks?per_page=100" \
  -H "Authorization: Bearer $GOOGLE_API_KEY"
```

### 4. Monitor `X-RateLimit-Remaining` proactively

Don't let your code discover the rate limit by hitting `429`. Instead, inspect `X-RateLimit-Remaining` on every response and slow down voluntarily when the value drops below a safety threshold (e.g., 10% of your plan's limit).

```javascript
function checkRateLimitHeaders(response) {
  const remaining = parseInt(
    response.headers.get("X-RateLimit-Remaining") ?? "999",
    10
  );
  const limit = parseInt(
    response.headers.get("X-RateLimit-Limit") ?? "999",
    10
  );

  const pctRemaining = remaining / limit;

  if (pctRemaining < 0.1) {
    console.warn(
      `⚠️  Only ${remaining}/${limit} API requests remaining in this window. ` +
      `Consider slowing your request rate.`
    );
  }
}
```
